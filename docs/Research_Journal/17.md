## 1. Rank Progression Chart — Axis Labels and Rendering Quality

The rank progression chart introduced in Entry 16 used `st.line_chart`, which renders without axis titles or tick control. This was replaced with an Altair-based chart (`render_rank_progression_chart`, defined once near the top of `experiment_app.py` and reused by both Tab 4 and Tab 11) that provides:

- A labeled x-axis (`Sweep Step (0 = Baseline)`) with integer-only ticks.
- A labeled y-axis (`Target Rank (lower is better)`) with an inverted scale, so an improving (lower) rank reads as an upward-moving line rather than downward.
- A dashed reference line at Rank #1.
- A distinct marker (red diamond) at the best-so-far step, with hover tooltips on all points showing the step label, rank, and target probability.

## 2. Cumulative Sweep Mode

### Motivation

The original design of the Hybrid Mute & Boost sweep (predating the GPU-batching work in Entries 14–15) piled candidate features on one at a time — Mute 1, then Mute 1+2, then Mute 1+2+3, and so on — continuing until the target reached Rank #1. The current sweep instead relies on user-specified batch-size lists (default `1, 3, 5`), which skip intermediate steps. With candidate ranking and safety filtering now batched and effectively free in wall-clock terms (Entry 15), the fixed cost of running a finer-grained, fully incremental sweep is no longer the limiting factor it originally was — only the sweep's own forward passes still scale linearly with step count, as discussed in the prior session.

### Implementation

Both Tab 4 and Tab 11 gained a checkbox — **"🔁 Cumulative Sweep (pile on one feature at a time until Target reaches Rank 1)"** — that, when enabled:

- Disables the Mute Batch Sizes and Boost Batch Sizes text inputs (`disabled=cumulative_sweep_4` / `disabled=cumulative_sweep_11`), since they are ignored while this mode is active.
- Replaces the batch-size–derived combination list with a paired, symmetric sequence generated from the post-safety-filter candidate pool sizes:

```python
max_pile = min(len(comp_ids), len(target_ids))
combo_pairs = [(n, n) for n in range(1, max_pile + 1)]
```

- Reuses the existing `stop_on_rank1` behavior and best-so-far tracking (Entry 16) unchanged — the sweep still halts the moment the target reaches Rank #1, and the best result across all executed steps is still what gets reported, not merely the final one.

The sweep loop itself was refactored from a nested double loop (`for m_n in mute_sizes: for b_n in boost_sizes:`) to a single loop over a precomputed `combo_pairs` list, since a symmetric cumulative sweep and an arbitrary batch-size grid are both just lists of `(mute_size, boost_size)` pairs — this removes the need for divergent loop structures between the two modes. `n_combinations_total` (used for the "Combinations run: X / Y" display) now derives from `len(combo_pairs)` rather than `len(mute_sizes) * len(boost_sizes)`, which would have been incorrect for the cumulative case.

### Scope

This mode is available identically on Tab 11's sequential and batched runs, so a cumulative sweep can still be timed head-to-head the same way the grid sweep is (Entry 15).

## Verification

Manually run on Tab 4 with the default test case (`"Seiyu Group's headquarters are in"` → `Tokyo`): with Cumulative Sweep enabled, the batch-size inputs correctly disabled, the sweep executed Mute 1/Boost 1 as its first (and only, in this case) step, reached Rank #1, and was correctly recorded as the best-so-far result with `n_combinations_total = 1`. A second test against a harder case (`"The headquarter of Army of the Guardians of the Islamic Revolution is in"` → `Tehran`, baseline rank 84) was attempted to confirm multi-step piling behavior, but the automated browser session's field updates did not propagate to the running app before submission; the underlying pairing logic was instead confirmed correct by code inspection (`combo_pairs` construction, loop refactor, and `n_combinations_total` fix). Re-verification against a harder case is worth doing manually.
