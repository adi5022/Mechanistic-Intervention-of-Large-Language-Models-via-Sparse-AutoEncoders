# Research Journal Entry 19: Why the Cumulative Sweep Stopped Early, and the Pool-Refill Implementation

**Date:** September 24, 2026
**Author:** Adi
**Branch:** `pool-refill-implementation` (branched from `stable-batched-workflow`)
**Focus:** Diagnosing why Tab 4's Cumulative Sweep ended before the target token reached Rank #1; replacing the single up-front candidate pool with adaptive rounds ("pool refill") and making the run state visible in the UI.

---

## 1. The Observation

A run with target token `black` improved from rank 10 to rank 5 and then stopped, with 24 mute / 24 boost features applied and no iteration limit set. Raising `Top N Candidate Features` to 100 did not help: the run stopped at 28 mute / 28 boost.

## 2. Diagnosis

There is no iteration cap in the code. The sweep length was fixed before it started:

```python
max_pile = min(len(comp_ids), len(target_ids))      # experiment_app.py, Tab 4 (old)
combo_pairs_4 = [(n, n) for n in range(1, max_pile + 1)]
```

`comp_ids` / `target_ids` are the candidates that *survived the safety filter*, not the raw Top-N lists. The filter (`check_target_safe*`, `check_boost_safe*`) rejects any feature that, applied alone, worsens the target's rank or drops its probability by more than 1e-6. For a low-ranked target most candidates fail it, so only ~28 per side survived regardless of N. The sweep stops when the smaller pool is used up; the only early exit is reaching rank #1.

Two structural properties made this worse:
- Sweep length is `min(mute pool, boost pool)`, so the smaller pool caps the larger one.
- Candidates were ranked and safety-tested once, against the **clean** model. After 10+ features are applied, the model's state (target rank, blocking token) is different, so that snapshot is stale.

## 3. A Second, Deeper Limit Found During Implementation

Candidates come from `get_top_active_features`, i.e. SAE features that are **active (>0) at the final token** at the hook point. Raising Top N only helps up to the number of active features. For `"The leading cause of death in men is"` at layer 8 that number is **67**. Also, scaling a feature (mute x0.7, boost x1.5) can never activate a feature that is currently zero, and the hook point sits upstream of every intervention, so steering does not change which features are active. The active set is therefore a hard ceiling on how many distinct features any sweep can use at this layer/position. Pool refill re-scores and re-filters within this set; it cannot extend it.

## 4. Design Decisions (agreed 2026-09-24)

1. **Pool refill:** when a round's pool is exhausted and the target is not Rank #1, keep every applied feature, run one fresh forward pass to obtain a new *steered baseline*, re-rank and re-filter candidates against that state, and continue. Repeats until Rank #1, a dead end, or an optional round cap.
2. **Rejected features are retried** in later rounds (a feature's effect depends on what is already applied). The UI reports whether each retested feature is now safe or rejected again.
3. **Regressing rounds are tracked, not rolled back.** Best-so-far tracking is unchanged and still reports the best state ever seen.
4. **Scope:** Tab 4 only. Tab 11 is unchanged.
5. **No default round cap.** "Max Refill Rounds" is optional (0 = unlimited). Termination is guaranteed because every round applies at least one new feature and the active set is finite.
6. **Independent growth inside a round:** step k uses `min(k, M)` mutes and `min(k, B)` boosts, running to `max(M, B)` instead of `min(M, B)`.

## 5. Implementation

**`src/hooks.py`** — `build_scale_map`, `with_extra_scale`, `make_scale_map_hook` (single encode/decode delta-patch scaling an arbitrary set of features), and `make_per_row_scale_hook_with_base` (batched: every row carries the already-applied set, plus one extra feature per row, in the same single SAE round-trip, so no chained-hook error as in Entry 18 section 4).

**`src/batched_eval.py`** — both batched primitives accept `base_scale_map`; when empty/`None` the original hook is used, so existing behaviour is unchanged.

**`src/editing.py`**
- `build_steered_context(model, sae, clean_ctx, base_scale_map, target_token_id)`: a `CleanContext` whose distribution/rank/probability come from a pass with the applied features active. `resid_last` is reused from the clean context (the hook point is upstream of all interventions).
- `get_top_active_features`, `get_top_competitor_features`, `get_top_target_features`: new `exclude_ids` (removed *before* the Top-N cut, so a refill reaches deeper) and `base_scale_map`.
- `check_target_safe`, `check_boost_safe`, `check_target_safe_batch`, `check_boost_safe_batch`: new `base_scale_map`; baseline comes from the steered context.

**`experiment_app.py` (Tab 4)** — the sweep is now a round loop. New controls: "Pool Refill" (on by default, active only with Cumulative Sweep) and "Max Refill Rounds" (0 = unlimited). The blocking token each round is the steered model's current top-1, not the clean one.

**Visibility added:**
- live status line (round, step, rank, probability, top-1, applied counts, best so far)
- per-round baseline card: clean vs previous vs new baseline, with rank change
- per-round pool table: Top N requested, active features available, candidates evaluated, safe, rejected
- "previously rejected features re-tested" table with the new verdict
- per-row line: rank vs the round baseline and vs the clean prompt
- run summary: rounds, features applied, steps, forward-pass count by category, stop reason
- per-round timeline table and a refill event log
- rank chart with dotted markers at each refill
- applied-features ledger and all-rounds rejection list (with Neuronpedia links); stopwatch now sums ranking/filter time across rounds
- run history record gains `pool_refill`, `max_refill_rounds`, `rounds`, `stop_reason`, `forward_passes`

If the target is already Rank #1 at baseline the run now says so instead of trying to suppress the target itself.

## 6. Verification

`scratch/validate_pool_refill.py` (all PASS):
1. Steered context equals the sweep's own combined-hook pass: max |dp| = 0.
2. Steered competitor ranking: batched and sequential orderings identical, max delta difference 1.1e-7, and no applied feature leaks into candidates.
3. Steered safety filter, batched vs sequential: 24/24 boolean agreement.
4. Empty base map is bit-identical to the original code path.

End-to-end in the app (`"The leading cause of death in men is"` -> `violence`, layer 8):
- Top N = 10: 9 rounds, rank **152 -> 50**, refill event log shows each new baseline; stopped because no unapplied active feature remained.
- Top N = 100: round 0 applied 32 mute / 49 boost and consumed all 67 active features, so the refill correctly reported there was nothing left (the ceiling in section 3).

## 7. Open Observations (not changed)

- Within one round a feature can land in both the mute pool and the boost pool. `make_mute_and_boost_hook` then multiplies both scales (x0.7 x x1.5 = x1.05), a near no-op that still counts as an applied feature on both sides. This predates this work; later rounds exclude any feature applied on either side.
- The number of active features at the hook position (67 here) bounds any single-layer, single-position, multiplicative intervention. Getting past it needs a different intervention mechanism, not a bigger pool.

## 8. Follow-up (same day): clearer baseline cards and a top-of-page live tracker

- **Baseline cards.** The original "Previous baseline" card showed where the previous round *started*, which duplicated the clean baseline and read as if the rank had not moved. Rounds after the first now show three cards: (1) original prompt (never changes), (2) how the previous round went, start -> end (rank, probability, applied-feature counts), (3) where this round starts (= where the previous round ended, plus the blocking token). A warning appears when a round did not improve the rank.
- **Live tracker.** A bordered panel directly under the Run button updates throughout the run: current phase, rounds finished, steps, current and best rank, applied-feature counts, a per-round table (start rank, end rank, best rank, safe pools, steps, status) and a rank chart with refill markers. It switches to a final success/warning banner with the stop reason. The existing in-flow live status line and all other sections are unchanged.
- **Observation from a user run.** A refill round ended at the same rank it started (#5) with no improvement, consistent with section 3: after round 0 applied most active features there was little left for the refill to re-rank.
- **Deferred.** Multi-layer intervention is being evaluated separately and is not implemented here.

## 9. Overlap fix (same day)

**Problem.** The safety filter tests each feature alone and one side at a time (mute-safe, boost-safe). It never compares a feature's two roles, so a feature that barely affects the target passes both tests and lands in both pools. Applied together it is scaled x(1-0.3) x (1+0.5) = x1.05, a near no-op that still consumes a feature slot on both sides. Evidence: pre-fix runs applied 34+41 = 75 and 32+49 = 81 feature slots from only 67 active features.

**Fix (Tab 4, `build_pools`).** After the safety filter, any feature safe on both sides is assigned to exactly one side:
- Safety filter on: compare the target-probability change from the mute test vs the boost test (same units) and keep the side that raises the target more.
- Safety filter off: keep the side where the feature ranks higher in its own list.
Applies in every round and in non-cumulative mode too. The UI shows the count, an expandable table (both deltas and the side kept), and an overlap column in the pool table; the event log and per-round records include `overlap_resolved`.

**Result** (`"The leading cause of death in men is"` -> `violence`, layer 8):
- Top N = 10: overlaps resolved 2 + 3 features across rounds; final applied set is 67 features total with zero shared between mute and boost (was 75 slots). Best rank #50 (unchanged).
- Top N = 100: 14 overlapping features resolved in round 0 and 3 in round 1 (matches the >= 14 estimated from the arithmetic); 28 mute + 39 boost = 67 = all active features, best rank #51 (previously 32 + 49 slots).
- Conclusion: the fix removes wasted slots and makes the counts honest, but it does not raise the ceiling (section 3): every active feature is still used, and the rank plateau (#50-51) is the same. Getting past it needs more candidate features, not better assignment.

## 10. Candidate source: all prompt positions, and a Top N cap (same day)

**Why.** In the `"The sky is"` -> `black` run (Top N 250, mute 0.5, boost 0.7) all 57 active features were consumed in round 0 and the target stalled at rank #5 (4.36%). Those 57 features come only from the last token (`is`), which mostly carries grammar features (e.g. "the verb 'is' at the beginning of sentences"). The sky/colour content sits at the earlier token `sky`, whose features were never candidates. The edit hook already scaled each selected feature at every position; only the *candidate list* was limited to the last token.

**What changed.**
- `CleanContext` now also stores `resid_all` (residual stream at the hook point for every position); `build_steered_context` carries it over.
- `get_top_active_features(..., positions="last"|"all")`: `"all"` encodes every prompt position, drops BOS, and scores each feature by its maximum activation over the remaining positions. `get_top_competitor_features` / `get_top_target_features` forward `positions`. Default stays `"last"`, so Tab 1-3, Tab 11 and the benchmark runner are unchanged.
- Tab 4: new "Candidate source" radio (default "All prompt positions"). The hook, ranking passes, safety filter, overlap fix and refill logic are unchanged.
- **Top N is now a true maximum.** Effective Top N = min(requested, unapplied active features for the chosen source), computed per round. The pool table shows Requested / Available / Evaluated, a caption states when the cap applied, and the pool summary lists active-feature counts per prompt token (BOS excluded). Run history records `candidate_source`.

**Verification.** `scratch/validate_pool_refill.py` (all PASS), new checks 5-7: for the "leading cause of death" prompt the last-token set (67) is a strict subset of the all-position set (303); all-position competitor ranking matches between batched and sequential paths (max delta diff 4.8e-7); the steered all-position target ranking matches and leaks no applied feature.

**Result on the `"The sky is"` -> `black` run** (Top N 250 requested, capped to 92; mute 0.5, boost 0.7):
- Active features per token: `The` 8, `sky` 34, `is` 57 -> 92 distinct (was 57).
- Round 0 applied 40 mute / 51 boost (7 overlaps resolved) and reached rank #4; round 1 had one safe boost left; round 2 had none. Total 40 mute / 52 boost = 92.
- Final: rank **#4** at 4.99% (previous last-token-only run: #5 at 4.36%). The blocker at the end is `blue`.
- Takeaway: the wider pool helps only slightly (35 extra features bought about one rank). The target still needs a much larger probability shift than the fixed-strength scaling of all available features provides; the pool is again exhausted.
