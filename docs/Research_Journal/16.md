# Research Journal Entry 16: Best-So-Far Result Tracking and Rank Progression Visualization

**Date:** September 18, 2026
**Author:** Adi
**Branch:** `layer-intervention-benchmark`
**Focus:** Correcting result reporting in the Hybrid Mute & Boost sweep (Tab 4, Tab 11)

---

## Problem Statement

During manual testing of harder test cases from `src/fact_bank.py` (e.g. baseline target rank 84), the target token's rank was observed to fluctuate non-monotonically across sweep steps rather than improving consistently. This raised the question of whether the safety filter introduced in prior work (Entry 12–14) was failing to hold gains once achieved.

Investigation showed this is not a defect in the safety filter, but a scope limitation in what it was designed to guarantee:

- `check_target_safe` / `check_boost_safe` (and their batched counterparts) evaluate each candidate feature **individually**, in isolation, against the clean baseline — prior to the sweep. A feature passes if muting/boosting it alone does not harm the target relative to the clean baseline.
- The sweep loop (`experiment_app.py`, Tab 4 and Tab 11) then constructs combinations by taking increasingly long prefixes of the ranked, safety-filtered candidate lists (`comp_ids[:m_n]`, `target_ids[:b_n]`) and applies each combination in a single joint forward pass.
- No mechanism compared a given combination's result against the best combination already observed in the same sweep — each combination was only ever compared against the clean baseline (via `check_combination_safe`), not against prior sweep steps.
- The value reported at the end of a run was whichever combination executed **last**, regardless of whether an earlier combination had produced a better (lower) target rank.

The net effect: individually-safe features could combine into a worse outcome than a smaller subset of the same features, and the UI had no way to surface or preserve the better result once a worse one ran afterward.

## Changes Made

### 1. Best-so-far result tracking (Tab 4 and Tab 11)

Both the interactive Tab 4 workflow and the `_run_hybrid_workflow` function backing Tab 11 now maintain a `best_so_far` state through the sweep, seeded from the clean baseline (`rank=clean_ctx.clean_rank`, `prob=baseline_target_prob`) and updated after every combination:

```python
is_new_best = (
    combo_rank < best_so_far["rank"]
    or (combo_rank == best_so_far["rank"] and target_prob > best_so_far["prob"])
)
```

Selection criterion: lowest target rank, ties broken by higher target probability. Each sweep row is now annotated in the UI as either a new best or a regression relative to the best already found, without altering the underlying sweep or safety-filter logic — this is purely a reporting-layer correction.

Downstream consumers were updated to use this tracked value instead of the last-executed row:
- The end-of-run summary panel ("Best Result Found During Sweep").
- The `run_record` saved to session history (Tab 4).
- The `final_top1` / `final_target_prob` fields consumed by the head-to-head comparison in Tab 11.

### 2. Rank progression visualization

A per-step record (`rank_progression`) is now collected alongside `best_so_far`, capturing target rank and target probability at each sweep step (Step 0 = baseline). This is rendered as a line chart (`st.line_chart`) immediately following the best-result panel, with target probability available as a secondary view. This gives a direct visual read on whether a sweep is converging toward rank 1 or oscillating, without manually cross-referencing the per-step tables.

## Scope and Limitations

- This change is a **reporting correction**, not a search algorithm change. The sweep still evaluates combinations in the same order, with the same cumulative prefix construction (`comp_ids[:m_n]`); no new combinations are explored and no additional forward passes are introduced.
- The underlying reason a later combination can underperform an earlier one is unchanged: appending more individually-safe features to a mute/boost set is not guaranteed to be monotonically beneficial in combination. This tracking makes that behavior visible and ensures the best observed result is not discarded, but does not prevent the regression from occurring.
- `check_combination_safe`'s "new blocker" detection is unaffected and continues to operate independently of this tracking.

## Verification

Manually verified on both tabs using the default test case (`"Seiyu Group's headquarters are in"` → `Tokyo`, baseline rank 2): the sweep reached rank 1 at Mute 1 / Boost 1, correctly flagged as a new best, and the best-result panel and rank chart both reflected this. Tab 11 confirmed the same tracking independently on both the sequential and batched execution paths.
