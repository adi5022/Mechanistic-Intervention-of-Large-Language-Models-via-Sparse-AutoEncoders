# Research Journal Entry 15: Making the Hybrid Sweep Faster, and Proving It

**Date:** September 18, 2026
**Author:** Adi
**Branch:** `layer-intervention-benchmark`

---

## What I was trying to fix today

Every time I use Tab 4 in the app (the "Hybrid Mute & Boost" tab, where I mute the competing tokens and boost the target token at the same time, trying different combinations until the target word wins), it always felt slow. My hunch was that it's slow because it was doing everything one small step at a time — checking one candidate feature, waiting, checking the next one, waiting again, and so on — instead of asking the GPU to just chew through all the candidates at once. GPUs are built for exactly that kind of "do a hundred things in one go" work, so running them one-by-one felt like a waste.

So today's goal was simple: **take that one-at-a-time process and turn it into a batched, GPU-friendly process**, and then actually prove — with a stopwatch, not vibes — that it's faster and that it still gives the same answer.

## What I actually changed

1. **Ported the batching over to the real app.** The batching trick itself already existed in the benchmark code (from a while back), but Tab 4 in `experiment_app.py` — the actual interactive app I use day to day — was never updated to use it. So I wired it in: same logic, same decisions about which features are "safe" to mute or boost, just run as one big GPU call instead of a loop of small ones.

2. **Built a side-by-side comparison tab (Tab 11).** This is the important part. I didn't want to just take my word for it that it's faster — I wanted to literally watch both versions run the *entire* Tab-4 workflow back to back, on the exact same prompt, and see the clock. So Tab 11 now runs:
   - the **original version** (the one the app first shipped with, everything sequential), and
   - the **new batched version**,
   
   one right after the other, on identical inputs. Every single detail Tab 4 normally shows is still there for both runs — which features got muted, which got boosted, the full top-5 token table for every mute/boost combination it tried, and (this is the part I initially forgot to carry over) which candidate features got **rejected** by the safety filter and why. Nothing is hidden or summarized away — it's the same level of detail as Tab 4, just doubled up so I can compare.

   **How the timer actually works, for the record:** it's a real stopwatch, not a diff of logged timestamps or an estimate. I call Python's `time.perf_counter()` once right before the very first (clean baseline) forward pass, and once right after the very last forward pass finishes — and on the GPU I force a `torch.cuda.synchronize()` right before each of those two readings, so the clock doesn't stop until the GPU has actually finished its work, not just until Python finished *asking* the GPU to do it. So the number on screen is genuinely "how long did this take, start to finish," including the ~60 individual forward passes the original version spends just ranking and safety-checking candidates before the sweep even begins — that background cost is why the "original" number looks bigger than the handful of sweep rows alone would suggest.

## What I found

I ran it twice on the same test case (prompt: *"Seiyu Group's headquarters are in"*, target: *"Tokyo"*):

- **Run 1:** Original took **12.16 seconds**. Batched took **0.90 seconds**. That's about **13.5x faster**.
- **Run 2:** Original took **11.55 seconds**. Batched took **0.71 seconds**. That's about **16.3x faster**.
- **Run 3 (after adding the detailed view back in):** Original took **11.75 seconds**. Batched took **0.58 seconds**. That's about **20.4x faster**.

Both runs landed on the exact same result — target word "Tokyo" jumped to rank #1, same confidence (13.42%), same features picked for muting and boosting. So this isn't a case of the fast version cutting corners and getting lucky; it's doing the identical work, just not wasting time doing it one piece at a time.

Honestly, seeing 12 seconds shrink to under a second was more dramatic than I expected going in. I knew batching would help, but I didn't think it'd be a 13-16x difference on a single sweep — that's the kind of thing that actually changes how I'll use the tool day to day, since I won't think twice about running a few more experiments back to back now.

## A bug I caught while wiring up the timer, worth writing down

While building the stopwatch display directly into Tab 4, my first version showed the original method taking **46 seconds** — way more than the 10-12 seconds I'd seen elsewhere. Turned out the timer was innocent; the safety-filter rejection messages in Tab 4 each call out to Neuronpedia over the internet to fetch a human-readable description of the rejected feature (for the little hover link), and that network round-trip was happening *inside* the part of the code I was timing. So the "slow" number wasn't measuring the GPU at all — it was measuring my internet connection talking to Neuronpedia, up to 30 times in a row.

Fix was straightforward: collect the rejection info as plain data first (just the feature ID and the number), keep that inside the timed section, and only look up the pretty descriptions from Neuronpedia *after* the clock has already stopped. Once that was separated out, Tab 4's own stopwatch settled down to a real **~1 second** with batching on, versus **~10 seconds** with it off — which lines up with everything else I measured today. Small thing, but it's a good reminder to double check *what* a timer is actually wrapping before trusting the number it spits out.

## Tab 4 now has an on/off switch, plus its own stopwatch

Since Tab 4 is the one I actually use day to day (Tab 11 is more of a "prove it" side panel), I added:

- A checkbox — **"⚡ Use GPU-Batched Optimization"** — right there in Tab 4's settings, on by default. Flip it off and Tab 4 falls back to the exact original one-candidate-at-a-time method. This means I don't need to jump to a separate tab just to feel the difference; I can toggle it on the same screen I actually work in.
- A stopwatch panel that appears after every run, broken into three honest numbers: time for the baseline pass, time for candidate ranking + safety filtering, and time for the actual mute/boost sweep. That breakdown is what let me catch the Neuronpedia bug above — without it, I'd have just seen one big scary number and had no way to tell where it was coming from.

With the checkbox ON: **~1.0 second**. With it OFF: **~10.1 seconds**. Same prompt, same target, same result (Tokyo at rank #1, 13.42%) — about **10x faster**, measured on the tab I'll actually be using tomorrow, not just in a side comparison.

## One more thing: a second stopwatch for "how long did I actually wait"

Fair question I got asked after showing the compute-only numbers: *if the Neuronpedia lookups still happen, doesn't the total time I experience still include them? What's the point of a number that hides part of the wait?*

Totally fair — isolating the GPU/CPU time answers "did the optimization work," but it doesn't answer "how long do I actually sit here." So both Tab 4 and Tab 11 now show **two** numbers instead of one:

- **Model compute time** — the isolated, apples-to-apples number that answers "is the optimization real." Excludes network lookups on purpose, since those cost the same either way and depend on internet speed, not on the code.
- **Total wall-clock time** — the honest, everything-included number that answers "how long did I actually wait." This is the one that matches the clock on the wall.

In practice they usually end up close to each other (Neuronpedia responses are normally fast), but on a bad network day the wall-clock number is the one that will actually diverge from the compute number — and now both are visible side by side instead of just picking one and hiding the other.

## Why this matters going forward

This isn't just a benchmark-script party trick anymore — it's baked into the actual app I use, and I can turn it on and off myself whenever I want to sanity-check it. Tab 4 runs the batched version by default now, has its own stopwatch so I can see exactly where time goes on any given run, and Tab 11 sits right next to it as a fuller "don't trust me, check for yourself" side-by-side whenever I want the deeper comparison.
