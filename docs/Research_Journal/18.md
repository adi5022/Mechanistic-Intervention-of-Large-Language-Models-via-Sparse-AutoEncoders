## 1. Groq Model Deprecation

`src/explain.py` hardcoded `llama-3.1-8b-instant` as the default model for all Groq calls (`query_groq`, used by every XAI-generation function in the app). Per Groq's deprecation notice, this model — along with `llama-3.3-70b-versatile` — was deprecated on 2026-06-17 and shut down on 2026-08-16, meaning it has been non-functional for over a month.

**Fix:** default model changed to `openai/gpt-oss-20b`, Groq's recommended replacement.

**Secondary issue found during verification:** `gpt-oss-20b` is a reasoning model that spends part of its `max_tokens` budget on hidden chain-of-thought before writing a final answer. With the app's existing `max_tokens` values (150–200, sized for the old non-reasoning model), reasoning was consuming the entire budget and returning an empty `content` field — confirmed via a direct API call (`finish_reason: "length"`, `content: ""`, `reasoning` field non-empty). Fixed by adding `"reasoning_effort": "low"` to the request payload, which Groq documents as supported specifically for `gpt-oss-20b`/`gpt-oss-120b` (values: `low`, `medium`, `high`; default `medium`). Verified with a direct API call afterward — real content returned correctly.

## 2. Dynamic Explanation for "Best Result Found During Sweep"

The best-result panel in Tab 4 (introduced in Entry 16) displayed a fixed block of explanatory text on every run, regardless of what the run actually did. This was replaced with a call to a new function, `generate_best_result_explanation()` (`src/explain.py`), which sends the run's actual baseline rank/probability, best rank/probability found, which mute/boost sizes produced it, and whether the sweep reached Rank #1 or exhausted its candidate pool — and asks Groq to explain, in plain English, why that combination is reported as "best" and what the outcome implies for that specific prompt.

Behavior:
- If **Enable AI Explanations (Groq)** is on and a key is configured, the dynamic explanation renders in place of the old fixed text.
- If not, the original fixed explanation still renders, with an added note that enabling the sidebar toggle produces a per-run explanation instead.

This only touches Tab 4 — Tab 11's equivalent caption is a single short line and was left as-is.

## 3. Run-History Logging Bug: Cumulative Sweep Metadata

While reviewing an exported `session_benchmark_full_details.json`, both saved runs showed `"mute_sizes": "1, 3, 5"` and `"boost_sizes": "1, 3, 5"` even though the actual `hybrid_details` arrays clearly showed mute/boost sizes incrementing from 1 up to 16 and 19 respectively — i.e., Cumulative Sweep mode (Entry 17) had been used, but the saved record still reflected the disabled textbox's leftover placeholder value rather than what actually ran.

**Fix:** `run_record` in Tab 4 now includes an explicit `"cumulative_sweep": bool` field, and `mute_sizes`/`boost_sizes` are computed conditionally — when cumulative mode was used, they report the actual executed range and the candidate-pool ceiling (e.g. `"cumulative 1..16 (pool max 16)"`) pulled from `hybrid_details[-1]` and `combo_pairs_4`, rather than the raw (and in that mode, meaningless) textbox string.

**Verified:** re-ran with cumulative mode off — record correctly shows `"cumulative_sweep": false` and the literal textbox value (`"1, 3, 5"`).

## Analysis Note (from reviewing the flagged JSON)

Separately from the logging bug, the underlying reason both flagged runs failed to reach Rank #1 was investigated:

- Run 1 (`"...violence against men is"` → `"shooting"`): baseline target rank was **2370** out of ~50k vocabulary — an extremely low-prior completion for that exact phrasing. Even after piling on all 16 available post-safety-filter candidates, the best rank reached was ~952, nowhere close to the top given how far back it started.
- Run 2 (`"...leading cause of death in men is"` → `"violence"`): baseline rank **152**, improved to **55** by mute/boost size 19 — real, substantial progress — but the sweep stopped there because it had exhausted its candidate pool (`min(mute pool, boost pool)` after safety filtering), not because the method stalled. Remaining probability mass was dominated by stronger, more contextually obvious competitors (`" a"`, `" heart"`, `" suicide"`, `" cardiovascular"`).

Neither case indicates a defect — both are expected outcomes of a fixed-strength, pool-limited search against a genuinely hard target. Raising `Top N Candidate Features` and/or the mute/boost strengths would give Cumulative Sweep more room to keep improving before hitting its ceiling.

## 4. Rank Mismatch Bug: Chained Hooks vs. the Combined Safety-Check Hook

While reviewing a live run, the "Combination Safety Check" text reported the target at rank 5, but the displayed top-5 table for that same step showed no target token anywhere in it — an outright contradiction, since a token at rank 5 must by definition appear in a top-5 list computed from the same probability distribution.

**Root cause:** the sweep loop (Tab 4 and Tab 11) applied mute and boost as **two separate, chained hooks** on the same hook point:

```python
model.add_hook(hook_name, make_joint_ablation_hook(mute_batch, sae, strength=strength_mute))
model.add_hook(hook_name, make_signed_ablation_hook(boost_batch, sae, strength=+strength_boost))
```

Each of these hooks independently encodes into SAE feature space, decodes, and delta-patches the residual stream. Chained, the *second* hook operates on the *already-modified* output of the first — meaning the boost hook's "baseline" for computing its delta is the muted (not original) signal, and the SAE round-trip happens twice.

`check_combination_safe`, however — the function that produces the "Combination Safety Check" text — uses `make_mute_and_boost_hook`, which applies both mute and boost together in a **single** encode/decode pass "starting from the same original signal" (its own docstring). Because SAE reconstruction is not lossless, these two approaches are not numerically equivalent, and the sweep's own displayed rank/probabilities could silently disagree with the safety check's rank for the same nominal intervention.

**Verification:** isolated script comparing both hook strategies on a 21-mute/21-boost combination (mirroring the case that surfaced the bug) at strength 0.9:

| Approach | Target rank | Target prob | Top-1 |
|---|---|---|---|
| Old (two chained hooks) | 66 | 0.210% | " homicide" |
| New (single combined hook) | 59 | 0.224% | " homicide" |

Max absolute probability difference across the full vocabulary: 0.64% — small in absolute terms, but easily enough to shift rank ordering among closely-clustered tokens, which is exactly what was observed.

**Fix:** both sweep loops now use `make_mute_and_boost_hook` directly (the same function `check_combination_safe` already used), so the top-5 table, target probability, best-so-far tracking, and the Combination Safety Check's rank are all computed from the identical intervention and can no longer disagree. `make_joint_ablation_hook`/`make_signed_ablation_hook` remain in use elsewhere (Tabs 2 and 3, which only ever apply one kind of intervention at a time and were never affected by this).
