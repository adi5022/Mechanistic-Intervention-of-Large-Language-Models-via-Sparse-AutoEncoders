## 6. Notebook write-up: iterations and the current draft

The user asked for a notebook write-up of the gradient-descent idea, to be followed later by the additive fix and the analyses. Feedback history: version 1 (plain, with a comparison table) was replaced by a formal version (abstract, problem, method, results); the user rejected it ("starting from the problem statement, the book has it all"); a method-only version with formulas was rejected as "too technical"; the final request was a strict format that does not sound stupid, titled "A gradient descent based approach". The latest draft (not yet confirmed by the user) is:

---

### A Gradient Descent Based Approach

**1. Overview.** The approach edits a language model's internal features during a single forward pass so that the correct answer becomes its top prediction. Each feature gets its own adjustable multiplier. All multipliers are tuned together, on the specific prompt, by gradient descent. Nothing is trained in advance, and the model's weights are never modified. The edit is temporary and exists only for the duration of the pass.

**2. Candidate Features.** The model's internal state at layer 8 is decomposed into sparse autoencoder (SAE) features. For each prompt, the 200 features with the highest peak activation across the prompt's token positions are selected as candidates (the start-of-text token is excluded). Only these can be edited.

**3. The Multiplier.** Every candidate gets one multiplier that scales its activation: 1 leaves it unchanged, 0 removes it, 3 triples it. Multipliers are constrained to 0 to 3 and all start at 1, so the initial edit is no edit at all.

**4. Applying the Edit.** For each candidate, the edit computes how much its activation changes under its multiplier, expresses that change along the feature's decoder direction, and adds it to the layer-8 state at every prompt position. The model completes its forward pass from that state and the prediction is read at the final position. Only the change produced by the multipliers is added; the SAE's reconstruction error is never injected.

**5. The Objective.** Three goals: (1) make the answer win: the correct answer must outrank its strongest competitor by a set margin; (2) limit side effects: once the answer leads, penalise how far the model's other predictions have shifted (KL divergence); (3) keep the edit small: a mild penalty on large multiplier changes, weighted so altering strong features costs more. The first goal is always active; the second applies only once the answer leads, so the process first finds a working edit, then makes it gentler.

**6. Optimisation.** Each multiplier is controlled by one underlying number. At every step gradient descent works out how each should move and updates all together: 100 steps, learning rate 0.1, Adam optimiser. Gradients flow only to the multipliers; every model weight stays frozen.

**7. Selection and Verification.** The best edit over the 100 steps is kept: any edit that places the answer first beats any that does not; among successful edits the lowest objective wins; if none reaches first place, the lowest-objective edit is kept. The chosen multipliers are then applied to the full model through the same hook the baseline sweep uses; the reported rank, probability, top prediction and side-effect score come from that real forward pass. The tool flags any mismatch with the tuning pass (none in any recorded run).

**8. Configuration.**

| Parameter | Default | Role |
|---|---|---|
| Candidate features | 200 | How many features may be edited |
| Candidate source | All prompt positions | Alternative: last token only |
| Steps | 100 | Number of gradient updates |
| Learning rate | 0.1 | Size of each update |
| Rank-1 margin | 0.3 | Required lead over the strongest competitor |
| Side-effect weight | 3.0 | Strength of the side-effect penalty |
| Edit-size weight | 0.005 | Strength of the size penalty |

Implementation: `run_gradient_descent_edit` in `src/gradient_editing.py`.

---

## 7. Parameter explanations given (other than candidate features and steps)

Checked against `src/gradient_editing.py` and `experiment_app.py`.

- **Candidate source.** "All prompt positions" ranks features by peak activation anywhere in the prompt; "Last token only" uses features active on the final token. The 300-prompt run used "all positions"; the two were never compared.
- **Learning rate (0.1).** Step size on each multiplier's underlying number. Too small: crawls; too large: bounces. Hand trials at 0.11 to 0.15 barely changed the result.
- **Rank-1 margin (0.3 logits).** The required lead over the strongest rival (0.3 logits is about 1.35 times as likely). It sets the target of the rank term and also gates the side-effect term, which switches on only once the lead reaches the margin. Reported success is still plain rank 1 on the real model.
- **Side-effect weight (3.0).** Weight on KL(clean, edited) over all tokens except the target and the original top-1, renormalised, at the last position. A KL of 0.33 costs about as much as being 1 logit short on the rank goal. Higher: gentler edits, fewer fixes. Because of the on/off gate, prompts that never reach the margin get no protection (a hopeless target ended with KL 2.7). The Prototype-lab option "Always penalise side effects" charges the penalty from step one. The lower KL versus the sweep is partly by design.
- **Edit-size weight (0.005).** Penalty on the sum of |multiplier change| times each feature's share of total peak activation. Those shares sum to 1, so even tripling every feature costs only about 0.01 in total: a tie-breaker, not a real constraint.
- **Interaction and status.** The three loss terms trade off (win in logits, 3 x KL, 0.005 x size). The defaults are the same numbers the earlier network study used for its per-prompt tuning, not tuned for gradient descent. The only sensitivity check was by hand on one prompt ("The sky is" to "powder": #179, #164, #157), and the 300-prompt run used the defaults. A small validation sweep of the margin and the side-effect weight was offered, not run.

## 10. Answers prepared for three sceptical questions

1. **"Instruction-tuned models won't make the same mistake."** Instruction tuning changes behaviour, not stored facts: models still state wrong facts confidently, have cutoffs, and miss private or niche facts. GPT-2 small is a transparent testbed; the question is whether precise, inspectable internal edits are possible. Partly right: for everyday accuracy a larger instruction-tuned model beats GPT-2 small, so this is not a better chatbot.
2. **"Fine-tuning is better."** Different jobs. This edit is reversible, needs no dataset or training run, and can list which features it changed; fine-tuning is permanent and can degrade other behaviour. Partly right: no comparison with fine-tuning has been run, so superiority cannot be claimed. Adding a fine-tuning baseline and a fact-in-the-prompt baseline to the comparison (alongside ROME, IKE, DiffMean) would close the gap. The literature the handoff cites (AxBench) suggests prompting can beat SAE steering.
3. **"How would you scale this to production?"** Not claimed to scale today. Needs SAEs for the larger model (open suites exist for some); per-prompt tuning means about 100 forward and backward passes through the layers after the edit point, too heavy at serving time, so the realistic pattern is offline: tune edits for a known list of corrections, store multiplier sets, apply on a match. Generalisation to rewordings and leakage must be fixed first. What transfers regardless of size: the evaluation lessons and the per-prompt optimisation with a side-effect penalty.

One-line framing offered: "This isn't a replacement for fine-tuning or better models. It's a study of whether you can make small, reversible, inspectable edits to a model's internals, and of how to tell a real fix from just forcing a word out."

## 11. New idea discussed: the idea in reverse, as a content filter

The user proposed a model that runs on every prompt with a list of NSFW words and deranks any predicted top word that is on the list: the project's idea in reverse.

- **Why it fits:** suppression is the easier direction (it only needs to turn down features that are already active, which multipliers do well, so the risky additive edit is not needed); success is easy to define (banned word falls below top rank or under a probability threshold, no true answer required); the side-effect penalty, leak test and planned specificity benchmark carry over.
- **Main problem with the plain word-list version:** a decoding-time banned-token list (set the logits to minus infinity) is exact, nearly free and works on any model, so feature editing would not beat it.
- **Where it could add value:** concept-level suppression (synonyms, misspellings, euphemisms, multi-word phrases) by muting features for the concept; the research question is whether that catches what a word list misses without damaging benign text.
- **Design issues:** per-prompt tuning is far too slow (100 gradient steps), so the realistic design is one fixed set of multipliers tuned once on many prompts, always on, with side effects measured on a large benign set; multi-token words (the app scores only the last piece of a multi-token target); the model can route around a blocked word, so the edit must stay on while generating; legitimate medical, legal and literary use needs false-positive measurement; not a security guarantee (rewording and jailbreaks).
- **Suggested framing:** compare a decoding-time word list, a trained classifier and fixed SAE-feature muting on how much unwanted text each blocks, how much it catches when the wording changes, and how much benign text it damages.
